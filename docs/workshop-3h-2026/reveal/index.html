AppHost orchestration · same graph, two languages

C# and TypeScript express the same intent

C# AppHost

var api = builder.AddProject<Projects.Bookstore_API>("api");
builder.AddProject<Projects.Bookstore_Web>("web")
    .WithReference(api)
    .WaitFor(api)
    .WithExternalHttpEndpoints();
builder.Build().Run();

TypeScript AppHost

const api = builder.addProject('api', '../Bookstore.API/Bookstore.API.csproj');
await builder.addProject('web', '../Bookstore.Web/Bookstore.Web/Bookstore.Web.csproj')
  .withReference(api)
  .waitFor(api)
  .withExternalHttpEndpoints();
await builder.build().run();

Pattern: create resource → add relationship → add lifecycle constraint → expose only the edge that needs user traffic. TypeScript's generated .aspire/modules API is restored, not hand-edited.

Service Defaults · internals

One extension establishes four service guarantees

Real workshop code

public static TBuilder AddServiceDefaults<TBuilder>(this TBuilder builder)
{
    builder.ConfigureOpenTelemetry();
    builder.AddDefaultHealthChecks();
    builder.Services.AddServiceDiscovery();
    builder.Services.ConfigureHttpClientDefaults(http =>
    {
        http.AddStandardResilienceHandler();
        http.AddServiceDiscovery();
    });
    return builder;
}
Observe — logs, HTTP/server/runtime metrics, distributed traces, OTLP export
Survive — standard HTTP retry/timeout/circuit-breaker policies
Discover — named endpoints resolve through HTTP clients
Report health — /alive answers “process responsive?”; /health answers “ready?”

Debugging angle

If no trace appears, confirm the service calls AddServiceDefaults(), the app calls MapDefaultEndpoints(), and AppHost injected OTEL_EXPORTER_OTLP_ENDPOINT. Health requests are intentionally filtered from traces to reduce noise.

Concepts you must understand first · before Lab 1

Why this concept matters

A distributed app needs one source of truth for what runs, how parts relate, when they are ready, and which concerns every service shares.

Core building blocks

AppHost declares resources; references pass config; endpoints expose protocols; lifecycle moves resources through starting/running/stopped; health reports readiness. Service Defaults centralize telemetry, health endpoints, discovery, and resilient HTTP.

Common mistakes

  • Treating AppHost as business code
  • Assuming Service Defaults starts resources
  • Confusing a project name with its resource name
  • Reading “Running” as “Healthy”

What success looks like

You can read Program.cs as a graph, identify endpoints/references, distinguish lifecycle from health, and explain why shared defaults live outside each service.

Instructor explanation · 4 minutes: Draw AppHost → resources → references/endpoints. Contrast “process started” with “ready.” Connect each Service Defaults extension to the dashboard signal it enables.

Transition to Lab 1: students will locate this exact graph in C#/TypeScript, find the four defaults in code, and prove running + healthy are distinct.

Concepts you must understand first · before Lab 2

Why this concept matters

Ports change and failures cross service boundaries. Discovery removes copied addresses; observability tells you which boundary failed.

Core building blocks

  • Expecting a reference to wait for readiness
  • Starting with random logs instead of resource health
  • Reading one service's log without the trace

Integrations · architecture pattern

Every integration has a hosting half and a client half

AppHost: create + connect

var cache = builder.AddRedis("cache");
var cosmos = builder.AddAzureCosmosDB("cosmosdb")
    .RunAsEmulator()
    .AddCosmosDatabase("cosmos");
var queue = builder.AddAzureStorage("storage")
    .RunAsEmulator()
    .AddQueues("queue");

api.WithReference(cache).WithReference(cosmos).WithReference(queue);

API: consume by the same names

builder.AddRedisOutputCache("cache");
builder.AddCosmosDbContext<BookstoreDbContext>("cosmos");
builder.AddAzureQueueServiceClient("queue");

Matching resource names are the contract. Client integrations add SDK wiring, health checks, logging, and telemetry—not just a raw connection string.

Concepts you must understand first · before Lab 3

Why this concept matters

Each dependency solves a different problem: Redis reduces repeated work, Cosmos persists catalog state, and a queue decouples background processing.

Core building blocks

The hosting integration adds a resource; WithReference injects connection data; the client integration registers the SDK + telemetry; WaitFor gates consumers on health. Redis = cache, Cosmos = durable documents, queue = asynchronous handoff.

Common mistakes

  • Using cache as source of truth
  • Doing slow work inside the request instead of queueing
  • Adding infrastructure but not the client integration
  • Using sleeps instead of health-aware dependencies

What success looks like

You can justify each dependency, trace resource→reference→client, wait for healthy emulators, seed durable data, and invalidate cached reads after mutation.

Instructor explanation · 4 minutes: For Redis, Cosmos, and queue, ask “what problem does it solve?” Trace hosting resource → reference → client integration → one observable operation.

Transition to Lab 3: students will run this exact topology, seed Cosmos, prove cache invalidation, and find evidence of the queue-driven Worker path.

Concepts you must understand first · before Lab 4

Why this concept matters

An agent needs workflow guardrails so it selects the right AppHost, waits for readiness, reads evidence, and avoids guessed ports or unsafe process cleanup.

Core building blocks

The aspire router skill selects subskills: init, aspireify, orchestration, monitoring, deployment. Safe runtime flow: start --isolated → wait → describe/logs/traces → resource-scoped action → stop.

Common mistakes

  • Using run for a background agent
  • Polling guessed ports instead of wait
  • Omitting --apphost in this multi-AppHost repo
  • Changing code before reading signals

What success looks like

aspire agent init installs reviewed local skills; the router chooses a subskill; the agent reports structured state and exits with no orphaned AppHost.

Instructor explanation · 4 minutes: Show router→subskill dispatch, then narrate start→wait→describe→stop. Contrast human foreground run with agent background start.

Publish and deploy · lifecycle model

The same production model, different side effects

AppHost
production resource model
publish
generate artifacts
deploy
build/push/provision/install
destroy
remove tracked resources

Review boundary

aspire publish --list-steps discovers the pipeline; publish output can be scanned, diffed, policy-checked, or handed to GitOps.

Execution boundary

Deploy needs target identity/context. Destroy needs matching state and deliberate approval. Keep target, environment, output path, and AppHost arguments consistent.

Publish and deploy · concrete AppHost example

The target is selected in application-model code

Real Examples/AspirePublish/AppHost.cs

var target = builder.Configuration["Deployment:Target"] ?? "compose";
switch (target)
{
    case "compose":
        builder.AddDockerComposeEnvironment("env");
        break;
    case "k8s":
        var registry = builder.AddContainerRegistry("registry", registryHost);
        builder.AddKubernetesEnvironment("env")
            .WithContainerRegistry(registry)
            .WithHelm(h => h.WithNamespace("aspire-publish"));
        break;
}
Compose
Local OCI build + generated services/network/environment; no registry required.
Kubernetes
Registry + Helm chart + current cluster context; routing/TLS remain platform decisions.
Arguments after --
Flow into AppHost configuration: -- --target compose.

Concepts you must understand first · before Lab 5

Why this concept matters

Artifact generation is reviewable and reversible; deployment execution can build, push, provision, install, update, or delete real target resources.

Core building blocks

Publish evaluates the production model and writes target artifacts. Deploy executes target pipeline steps. Destroy tears down tracked resources. --list-steps previews the plan; --output-path keeps artifacts reviewable.

Common mistakes

  • Assuming publish installs the app
  • Running deploy without reviewing target/context
  • Committing generated secrets or deployment state
  • Automating destroy without explicit approval

What success looks like

You can preview steps, publish Compose artifacts, inspect workloads/config/networking, and explain exactly when side effects begin—without deploying in class.

Instructor explanation · 3 minutes: Draw a hard boundary between “write artifacts” and “execute against a target.” Connect the target switch to generated output and side effects.

Transition to Lab 5: students will preview all three pipelines, publish Compose output, and explain the generated workloads/config/network without deploying.
